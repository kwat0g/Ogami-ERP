## Layer model

Demo data is assembled in dependency-ordered layers registered in `config/demo.php` under `layers`. Each layer implements `DemoSeedLayer`; the `DemoSeeder` base class is available for Laravel-style seeder classes. A layer declares a stable key, the module names it covers, dependencies, and a `run(DemoSeedContext $context)` method.

`DemoSeedLayerRegistry` validates configured layers and dependency keys, rejects duplicates and cycles, and topologically orders the selected layers. `--only=<layer-or-module>` selects matching layers and includes their dependencies. Registered layers currently cover `organization`, `inventory-catalog`, `finished-product-catalog`, `production-assets`, `bom-routing-catalog`, `business-partners`, `workforce-identities`, `quality-plans`, `quality-inspection-specs`, `supplier-listings`, `maintenance-master-data`, `maintenance-spare-parts`, `opening-stock-balances`, `crm-pricing`, `purchasing-history`, `purchasing-receiving-history`, `quality-history`, `production-history`, `production-execution-history`, and `maintenance-history`. Each layer's dependency declaration in `config/demo.php` is authoritative. See the individual module notes for dependency chains.

`DemoSeedRunner` checks the production guard itself, resolves the selected layers, disables the active connection's query log, and executes each layer with a stable seed derived from the global seed and layer key. It reports layer start/finish events with elapsed time and peak PHP memory, collects cycles between layers, and wraps failures with the layer key. `DemoRecordRegistry` stores lightweight model-class/primary-key references between layers rather than retaining complete model collections.

`DemoSeedContext` contains the parsed as-of date, scale, seed, filter and no-history option; a fixed-seed `en_PH` Faker generator; the shared record registry; and helpers for acting as a user, controlling mutable and immutable Carbon clocks, and suppressing notifications around historical actions. The notification helper fakes Laravel's dispatcher and temporarily binds `DemoNotificationService` for direct `NotificationService` calls, restoring both bindings in `finally`, including when the action throws. Historical services that use either supported notification path therefore do not leave stale inbox rows. `DemoHistoricalNotificationSuppressionTest` exercises the real supplier-listing service: the live submission creates a reviewer notice; a historical submission creates no extra notice but retains its supplier-catalog outbox event. This addresses the direct-service gap tracked in F-019; other unmediated database writes still need to be checked as each module is added. Live scenario layers use normal notification delivery for currently open work. `workforce-identities` also uses a `finally`-restored, container-scoped `SettingsService` override during employee creation so the normal `EmployeeCreated` chain does not auto-create random-password accounts for historical roster records; it does not modify the persisted setting. Layers must use the clock helper around historical domain actions; the runner does not move application time globally because overdue and dashboard behavior follows runtime time.

`DemoSideEffectScope` temporarily switches every configured mailer transport to Laravel's in-memory array transport, every broadcast connection to the local log driver, every queue connection to synchronous execution, and every cache store to process-local array storage. It clears cached manager/connection instances before and after the scope and restores every prior config value in `finally`. Database-backed in-app notifications are controlled separately through the context helper. Real integrations must not be called from a demo layer.

## Write guard

All demo commands and legacy demo-seeder entry points call the shared `DemoSeedingGuard`. It refuses production and any environment other than `local`, `testing`, or `demo`; requires `DEMO_SEEDING_ENABLED=true`; requires an exact configured DB-name allowlist entry; permits `ogami_demo*` and `ogami_test*` in local mode, `ogami_demo*` in demo mode, and `ogami_test*` in testing; and checks the configured database host against the local-host allowlist. Production remains forbidden even if all flags match.

Set the variables only in an isolated demo environment. `.env.example` keeps the enable flag off and the allowlist empty:

```dotenv
DEMO_SEEDING_ENABLED=true
DEMO_SEEDING_DATABASE_ALLOWLIST=ogami_demo_thesis
DEMO_SEEDING_ALLOWED_HOSTS=localhost,127.0.0.1,::1,db
DEMO_ACCOUNT_PASSWORD=
DEMO_SNAPSHOT_DIRECTORY=
DEMO_PG_DUMP_BINARY=pg_dump
DEMO_PG_RESTORE_BINARY=pg_restore
```

Do not put production database names in the allowlist. The test bootstrap enables the guard only for its normalized `ogami_test*` database so tests can exercise guarded demo seeder code without widening the application database rule.

Browser fixtures that still depend on the legacy `DemoAccountSeeder` use `api/tests/Browser/demo_seed_helpers.php`. The helper requires a disposable `ogami_test_*` database, explicitly allowlists that exact database for the process, and runs the seeder inside the side-effect scope. Migrating E2E baselines to the shared `--scale=small` layers remains open until demo-account, transaction, and scenario layers are complete.

## Commands

| Command | Current behavior |
|---|---|
| `php artisan demo:seed [--as-of=YYYY-MM-DD] [--scale=small\|demo\|full] [--seed=N] [--only=layer-or-module] [--no-history]` | Parses options, checks the guard and layer plan, and runs registered reference layers plus current purchasing/receiving/AP, quality complaint, production-planning, and maintenance work history. Selected layers include their registered dependencies. Production execution/OEE, remaining transaction groups, and payroll history remain future work. |
| `php artisan demo:reset [--as-of=...] [--scale=...] [--seed=...] [--no-history]` | Checks the guard, the code-level readiness gate, and layer plan before `migrate:fresh`. The gate must stay false during staged implementation and may be enabled only after every required layer exists and `demo:verify` passes. |
| `php artisan demo:snapshot [--file=name.dump]` | Guarded PostgreSQL custom-format `pg_dump`; writes a SHA-256 manifest alongside the dump. Password is passed through the child process environment, not command arguments or manifest. |
| `php artisan demo:restore --file=name.dump` | Guarded restore to the same allowlisted DB name only; validates filename, directory, matching manifest, and checksum before `pg_restore --single-transaction`. |
| `php artisan demo:credentials` | Lists internal and portal accounts in the guarded demo database, including Gmail-based accounts; displays the configured shared demo password, if present. |
| `php artisan demo:verify` | Planned for Phase 6; not implemented in this tooling unit. |

Snapshots are stored in `DEMO_SNAPSHOT_DIRECTORY` or `api/storage/app/demo-snapshots`. Use backups only for the isolated allowlisted demo database. The restore command replaces database objects in that database.

For a deliberate defense seed in an existing live database whose name is outside the demo prefixes, the CLI process must run with `APP_ENV=demo`, `DEMO_SEEDING_ENABLED=true`, `DEMO_SEEDING_ALLOW_NON_DEMO_DATABASE=true`, and single-entry exact database and host allowlists. The override defaults to false, does not permit `APP_ENV=production`, and does not relax either allowlist. Never run `migrate:fresh`, `demo:reset`, or `demo:restore` against a live database; use only additive `demo:seed` layers.

## Legacy seeder boundary

`DatabaseSeeder` checks the guard before any baseline writes when `app.seed_demo_data` is enabled. Every direct legacy demo seeder entry point also checks the shared guard. In `local` and `demo` environments, that assertion additionally requires the active side-effect scope, so direct `db:seed --class=...DemoSeeder` calls and `DatabaseSeeder` with `SEED_DEMO_DATA=true` stop before writes; use the guarded demo commands instead. The test environment permits direct test seeder calls only against the exact `ogami_test*` allowlist, and PHPUnit pins mail, broadcast, queue and cache to fake/local drivers. The new commands do not call legacy demo seeders as a fallback. System/reference seeders remain available through the existing baseline pathway; the new data layers will replace demo fixtures module group by module group after their process behavior is verified. See [workforce-identities.md](workforce-identities.md) for the employee/service path and the narrowly scoped direct-account exception.

Current code moves `DemoBomCostBasisSeeder` from the reference-only list to the demo-only list because its rows are demo-specific. This is the only `DatabaseSeeder` grouping change in Phase 2.

## Opening stock baseline

`opening-stock-balances` covers Inventory and Purchasing because the normal movement outbox listener creates replenishment PRs for low opening stock. It depends on the BOM/product catalog, spare-part catalog, and workforce actor. It covers 58 / 138 / 178 catalog items at small/demo/full scale and uses `StockMovementService` for all positive opening balances, lots, stock levels, weighted-average cost and audit history. Read [opening-stock-balances.md](opening-stock-balances.md) for quantity bands, zero-start examples, auto-generated PR handling, the accounting boundary, and the current application limitation: opening stock movements are `not_required` for GL after the former combined opening-balance workflow was removed (F-025). The guarded small smoke created 53 movements for 52 items plus 16 event-generated draft PRs; SQL found zero stock/ledger mismatches, duplicate movement keys, negative balances, or historical notification rows. An identical rerun left the movement, stock, audit, and PR records unchanged. The focused test passes 1 test / 167 assertions; lint, Pint, and targeted PHPStan pass. The `RefreshDatabase` test transaction does not publish these after-commit events, so the console smoke is required to verify the derived PR records.
