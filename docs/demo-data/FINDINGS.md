| F-013 | DSS demo scenario test references an unregistered detector | Reproduced 2026-11-14 with `php artisan test tests/Feature/DSS/DssDemoScenarioSeederTest.php`: `DssDemoScenarioSeeder` runs `dss.work_order_intervention`, but `DetectorRegistry` throws `Unknown detector`; the test then cannot find the expected recommendation. No workaround or app fix applied. |
| F-014 | Staged layer registration could unlock a partial destructive reset | Adding the first layer makes the registry non-empty, which previously let `demo:reset` pass preflight and run `migrate:fresh` before the planned dataset existed. Addressed in the tooling branch by a code-level `demo.reset_ready` gate defaulting to false; it must remain false until all required layers exist and verification passes. |
| F-015 | Auxiliary equipment has no maintenance workflow target | Current `MaintainableType`, schedule resolution, and maintenance work-order validation support only `machine` and `mold`. Auxiliary plant equipment can be represented in the asset register but cannot receive maintenance schedules or work orders through the application's domain services. The production-assets layer seeds its auxiliary records as assets only; no polymorphic workaround or direct transaction insert is used. A separate application feature decision is needed before auxiliary-equipment PM history can be demonstrated. |
| F-016 | Production asset acquisition values have no authoritative source in the app | The current asset and machine/mold masters provide no reference acquisition-price catalog. The production-assets layer uses clearly marked synthetic estimates for capital costs, useful lives, salvage values, and running-hour opening values. They support demo navigation and asset-register display only; do not present depreciation, financial statements, or replacement-cost analytics as actual Ogami values until the owner supplies a source register. |
| F-017 | No released machine/mold capability register is available | The current product records contain no validated tooling assignment, mold drawing, cavity count, cycle time, or press-tonnage capability source. The layer uses illustrative values and compatibility bands so current MRP pages have linked master records; no customer drawing or engineering approval is implied. Production/tooling engineering values are needed before throughput or compatibility results can be presented as actual plant performance. |
| F-018 | BOM consumption and conversion rates have no approved manufacturing standard | The app has no released material weight, scrap/yield, packaging allocation, labor/machine/overhead rate, or per-operation time standard for these synthetic parts. The BOM/routing layer uses explicitly documented demo estimates, separate from payroll/statutory calculations. `RM-009` is added through `ItemService` for the `PA6 GF30` product specification on `HS-001`; its standard cost and planning levels are estimates. Validate with process engineering and Finance before presenting BOM costs or margins as plant facts. |
| F-019 | Historical notification suppression was incomplete for direct service notifications | `DemoSeedContext::withoutNotifications()` originally faked Laravel's notification facade, but `NotificationService` also persists database notifications directly. Domain events such as supplier listing submission could therefore leave inbox rows after the listing was later approved or rejected. The seeder-only scope now replaces both the Laravel dispatcher and app `NotificationService` during historical actions, restoring the previous bindings in `finally`; the unit test covers exception unwinding, and the supplier-listing integration test confirms a historical submission retains its catalog outbox event without adding a reviewer inbox notice while an unwrapped pending submission creates one. This does not change application logic. Other unmediated database writes remain subject to module-level review. |
| F-020 | Employee service path makes full workforce seeding exceed the target runtime in the current test environment | The focused feature test exercised 200 `EmployeeService::create()` calls in 529.24 seconds before a later account timestamp error; after fixing that error, the demo-to-full scale-growth integration attempt ran for over 14 minutes without completing and was stopped. Peak PHP memory observed was about 159 MiB. PostgreSQL activity showed repeated `event_outbox` payload updates during the run; this is evidence of work, not proof of the sole bottleneck. The layer chunks 25 employees per outer transaction but does not bypass EmployeeService, observers, audit or outbox behavior. No application logic was changed and no bulk-insert workaround was applied. The 200/240 write path and the under-10-minute full-seed target remain unverified; only roster planning and the small integration path are currently verified. Do not claim full-scale throughput until a bounded seeder-side profile or an approved design change resolves this. |
| F-021 | Supplier offer prices have no authoritative quote source | The current application has item standard costs and supplier listing price fields, but no released vendor quotation history for these synthetic supplier/item pairs. `supplier-listings` derives illustrative quotes as item standard cost × order-unit conversion quantity × a fixed vendor factor. The factors and order-unit conversions exist only to demonstrate approval, base-unit price synchronization, and sourcing; they are not market prices, vendor offers, or purchasing commitments. Validate price and pack-size data with Purchasing before presenting sourcing comparisons as Ogami facts. No application workaround is needed. |
| F-022 | Dependency audit and existing CRM PHPStan errors block CI on the demo PR stack | API workflow runs for PR #529, PR #530, PR #532, PR #533, PR #534, PR #537, and PR #542 stopped at `composer audit --locked` with 12 advisories across six packages; those demo branches do not change Composer files. PR #537, #538, and #542 finding-lifecycle checks pass; their API jobs stop at the inherited audit step before PHPStan or PHPUnit. The separate lock-only update in PR #531 passes local `composer audit --locked` and strict `composer validate` and gets past Composer in CI, but CI now stops at PHPStan with three existing errors: `$generatedPath` is undefined at lines 94–95 of `api/app/Modules/CRM/Controllers/CustomerAgreementDocumentController.php`, and the `runAsCustomerPortal()` template type is not referenced in a parameter in `api/app/Modules/CRM/Support/PriceAgreementAuditContext.php`. These files are unchanged by the demo and dependency PRs; PHPUnit is not reached remotely. The quality-plan and inspection-reference feature tests, related service tests, targeted PHPStan and guarded small console seeds pass locally. Resolve the dependency update and CRM static-analysis findings in their own reviewable units, then update the stacked demo branches before treating CI as green. |

| F-023 | Demo reset currently skips operational reference seeders required by demo layers | `DemoResetCommand` sets both `app.seed_reference_data` and `app.seed_demo_data` to false before calling `DatabaseSeeder`; `DatabaseSeeder` only invokes the operational reference group when either flag is true. This skips `ShiftSeeder`, `HolidaySeeder`, `LeaveTypeSeeder`, `DefectTypeSeeder`, and other reference rows, then the demo runner starts layers that require them. A guarded `demo:seed --only=quality-inspection-specs` run on `ogami_test` without first running the reference baseline failed in `workforce-identities` with `Shift Night Shift is missing`; rerunning after explicitly invoking the existing reference seeders succeeded. `demo:reset` remains disabled behind `demo.reset_ready=false`; do not enable it until the baseline/reset ordering is corrected in a separate reviewed tooling change. No app code was changed and no reset workaround was added. |
| F-024 | Inventory has no enforced spare-part-to-asset compatibility relation | `Inventory\Models\Item` stores item identity/classification and stock fields but has no machine or mold compatibility relation; maintenance records the item on a work order only after part usage. The new catalog records an intended equipment class in the synthetic item description and does not claim fitment enforcement. Spare-part compatibility filtering or validation requires a separate application feature decision; no schema workaround or raw relationship row was added. |
| F-025 | The combined GL/inventory opening-balance workflow was removed | Migration `0457_drop_performance_review_tables.php` states that the former go-live flow created a journal entry and an `opening` stock receipt, then removes its code path. `StockMovementService` and `StockMovementType::Opening` remain, while `MovementGlPostingService` explicitly marks opening movements `not_required`; no current combined opening-balance page or dedicated service remains. The demo stock layer can therefore establish and verify synthetic inventory quantities and costs, but it does not create a matching GL inventory opening journal or balancing equity line. No contra account or finance opening-entry policy was inferred. See [opening-stock-balances.md](opening-stock-balances.md); a finance-approved current workflow or account mapping is needed before claiming stock-to-GL opening reconciliation. No app workaround or direct journal write was added. |
| F-026 | Inventory GL handoff regression test leaves an after-commit chain step pending | Reproduced in the isolated `ogami_test` database with `php artisan test --filter=missing_gl_configuration_commits_stock_and_replays_idempotently tests/Feature/Inventory/MovementGlPostingTest.php`, and in the full targeted GL test file (8 passed, 1 failed). This regression does not exercise the opening movement path (`not_required`) and no application behavior was changed. The regression test / transaction integration needs separate review; do not treat that GL handoff path as verified by this unit. |

Portal notices use `sendPortalInApp()` separately and are not covered by this failure. The seeder does not insert replacement notification rows or alter app code. | F-028 | Customer selling-price and margin assumptions have no approved source | The current app has no approved customer selling-price list or released margin policy. `crm-pricing` uses reviewed unit cost × 1.20 for minimum price and × 1.50 for base/offer price, with illustrative volume tiers at × 1.45 and × 1.40. | F-031 | Manual supplier-dispatch alerts are suppressed by PO subject authorization | Reproduced repeatedly during the isolated Purchasing integration and guarded console runs when an approved PO had no active supplier portal recipient. `SupplierDispatchService::notifyPurchasing()` selects active users by the broad `purchasing.view` permission, then `NotificationService::sendForSubject()` checks `PurchaseOrderAccessPolicy`; every selected recipient failed the PO row-access check, producing `Notification recipients lack subject access; delivery suppressed` and no alert. The PO correctly remains `approved` with a `manual_required` dispatch ledger row, but the Purchasing inbox/notification does not direct a user to complete transmission. The layer does not insert a substitute notification or change role permissions. Correct the recipient query or access policy in a separate application-fix PR before claiming this alert path is covered. No workaround approval was requested or used. |
| F-032 | Purchasing history uses calendar-day offsets for approval and supplier-response timestamps | With `--as-of=2026-11-15`, `PurchasingHistoryLayer` places the `PO-SENT` request/submission on Saturday 2026-11-07 and approval on Sunday 2026-11-08. The `PO-ACKNOWLEDGED` PO is sent Saturday 2026-11-07 and accepted through the supplier portal Sunday 2026-11-08. The receiving layer's own receiving dates are business-day aligned, but it depends on these upstream states. This is a demo-data schedule issue, not an application process defect; it makes approval/dispatch timelines less plausible for a weekday-only office. No application logic or upstream seed schedule was changed in this unit; update the Purchasing history schedule in its own follow-up and verify it with weekday and weekend as-of anchors. |

| F-033 | Customer complaint enum states `investigating` and `cancelled` have no service transition | `ComplaintStatus` declares `investigating` and `cancelled`, but current `ComplaintService` lifecycle operations are `create`, `resolve`, and `close`; its transition matrix allows resolve from `open`/`investigating` and close from `resolved`. There is no service operation to begin investigation or cancel a complaint. `quality-history` seeds only service-reachable complaint states (`open`, `resolved`, `closed`) and does not write status fields directly. The two enum values remain unrepresented until the application exposes their supported lifecycle actions. No application change or workaround was made. |

| F-034 | Customer complaint creation does not create an internal in-app NCR notice | `ComplaintService::create()` calls `NcrService::create()` directly, then emits `CustomerComplaintUpdated`; the internal `auto_ncr_created` notice is sent by the inspection-failure handoff path, not by complaint creation. The seeded open complaints and linked NCRs are visible through their lists and dashboard data, but the current flow does not put an NCR notice in the QC inbox. The Quality layer does not insert a substitute notification because that would not represent the current application flow. Add and review a complaint-to-QC notification path in a separate application change if the thesis demo requires this inbox notice; this unit has no notification workaround approval. |

| F-035 | BOM routing replay treats temporary maintenance downtime as a missing route | `BomRoutingCatalogLayer` selected an idle/running compatible machine before checking whether an active route already existed. A released route remains valid while its machine is unavailable for maintenance. The demo seeder fix reuses that compatible machine for the existing active route and still requires an idle/running machine to publish a new route; no application lifecycle is bypassed and no raw write is used. Fix is isolated in its own reviewable PR. |
| F-036 | No QC-released finished stock is available for a portal order scenario | A focused O2C seed attempt using `CustomerPortalService::quoteOrder()` failed through `CustomerPortalOrderAvailabilityService::assertOrderAvailability()` with `Only 0.000 units are currently available for this stock item.` The existing production-execution demo output is intentionally partial/in-progress, so it is not outgoing-QC released saleable stock. The O2C layer therefore creates a legitimate internal draft through `SalesOrderService`, ready for Sales to confirm and start MRP; it does not fabricate a portal order, stock, delivery, or invoice. Review the finish-first/routing configuration and a released stock production path before adding portal-driven fulfilment. No application change or workaround was made. |
| F-037 | Existing product rows can lack metadata required by downstream demo quality references | The all-layer defense seed against the existing database reached `quality-inspection-specs` after `finished-product-catalog` and failed because existing `WB-001` had `specifications = NULL`. The failure is in existing data compatibility, not an application workflow bug. No stock, sales, or production transaction was directly written by the workaround. |
